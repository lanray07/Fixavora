# Release instructions — blocked development delivery

Do not submit this build until all mandatory criteria in the brief pass. No store submission or production deployment was performed.

1. Complete all UI translations (283 base keys), locale plural forms, regional terminology, privacy/support copy and linguistic review. Verify RTL, long text, font scaling, dates, currencies, voice dictionaries and accessibility. Keep `tools/localize.py validate` and `gradlew lintDebug` active. Do not bypass missing-translation errors.
2. Supply the publisher identity, support contact and privacy policy URL. Review the provisional Fixavora name and nearby names with appropriate trademark/marketplace checks. Confirm distribution rights/countries, age suitability and current Amazon policy requirements.
3. Register `com.fixavora.app` and the entitlement SKU `fixavora.premium.lifetime` in Amazon. Confirm package ownership before release; the ID is provisional. Set actual marketplace prices in the console. Add the app-specific public key (not a shared secret) to the ignored assets path.
4. Deploy the receipt API to approved infrastructure behind TLS and production rate limiting. Store `AMAZON_SHARED_SECRET` only on the server. Set `FIXAVORA_RECEIPT_ENDPOINT` for the Android build. Test real success/failure, cancellation, duplicate requests, restore pagination, refund/revocation, user changes and offline cache behaviour in Amazon App Tester and LAT. Keep all existing records accessible.
5. Complete all module UI journeys, attachment access and lost-file handling, reminders, backup picker/restore, report sharing, dark/high-contrast and accessibility checks. Test physical Fire tablet sizes/versions and orientations beyond the one recorded device. A compact viewport capture is not proof of phone compatibility. Recognition requires a compatible engine; the tested Fire has none. Verify supported TTS voices instead of advertising all target languages.
6. If remote AI is added, implement the real adapter and schema validation with explicit consent and a sustainable usage policy. Never ship a client API key or silently send property records. Current local assistant functions work without a remote model; no paid inference is included.
7. Generate eight real app screenshots per approved listing locale after translation completion. Run screenshot captures in the target locale and review headlines, clipping, readability, device type and claims. The included compositions are candidates, not approved store assets. Amazon listing support is separate from interface languages; see `docs/RESEARCH.md`.
8. Decide the signing/distribution route. Amazon documents applying its own signature whether an uploaded APK is signed or unsigned; verify the actual Amazon-signed candidate through LAT. For any separate publisher-signed distribution, create a key under publisher control, keep a secure recovery copy outside the repository, align/sign with Android tools and verify it. The delivered release APK is unsigned and is not a directly installable publisher-signed package.
9. Run unit, instrumentation, localisation, lint, privacy/security and Amazon billing checks against the final signed candidate. Regenerate the deliverable inventory with `python tools/package_delivery.py`. Review SHA-256 hashes and source revision.
10. Obtain explicit user authorisation for the actual store submission. Submit only when all mandatory acceptance criteria pass. Never infer publishing permission from a request to push source code to GitHub.

Current GitHub workflow runs build/tests and lint. Incomplete translations intentionally make it fail. GitHub artifact upload runs even after failures, but artifact presence is not release certification. The Windows environment initially lacked sufficient C: disk space for its existing emulator; no emulator configuration has been claimed as verified. The connected Amazon hardware is the evidence-backed runtime target.
